# Fixed ordinary boot policy tasks v1

Development contract, 2026-11-06. Current validation is recorded in the console review `docs/reviews/center-ordinary-boot-20261106.md` and its matching evidence JSON. The underlying [native boot policy contract](ordinary-boot-adoption-v1.md) remains authoritative. This adds bounded center tasks and administrative UDS methods, not a remote shell or Kura restart/reboot operation.

The default is disabled. A root-owned private `AGENT_ORDINARY_BOOT_REQUEST` selects exactly one local request file, containing the already reviewed native target, retired entries and independently sealed ordinary grant. Peers cannot provide a path, command, unit, grant or requested enablement. The startup request is checked for private ownership, exact fields and schema/lifetime; actual fixed inputs and current native states are checked again by prepare and execute. It creates no Kura startup dependency on the agent.

Enabling the variable alone does not grant filesystem writes through the default service sandbox. A separately reviewed systemd drop-in must permit the Core registration directory, native wants-link directory and shared lock location; keep the fixed request and sealed inputs read-only. An administrator must pre-provision the corresponding paths. Do not broadly weaken the service sandbox or enable this capability by default. The example `packaging/ordinary-boot.conf.example` is not automatically installed or activated.

The agent advertises `ordinary.boot.v1` only when the local fixed authority is configured. All five center operations require admin, CSRF, current gateway ownership and a fresh capability; dispatch also checks the current capability. Protocol-major 1 adds operations 15–19 and field 12 without changing old numbers:

| Operation | Input | Effect |
| --- | --- | --- |
| `ordinary.boot.status` (15) | none | Token-free latest transaction and separately validated confirmed policy |
| `ordinary.boot.prepare` (16) | none | New reviewable plan, before states, actions, grant digest, token and expiry |
| `ordinary.boot.execute` (17) | `ordinaryBootAction` | Execute the previously reviewed native policy once |
| `ordinary.boot.cancel` (18) | `ordinaryBootAction` | Cancel an unissued plan; retain earlier confirmed policy |
| `ordinary.boot.reconcile` (19) | none | Explicitly inspect existing results; no command replay |

`ordinaryBootAction` contains exactly canonical `transactionId=boot-<UUID>` and `confirmationToken=<UUID>`. Administrative UDS uses the same method names and payload. A registered Kura peer cannot gain these methods, even when its Unix UID equals the admin UID or it has remote-switch delegation. Boot status does not wait for the online write mutex; mutations share it with online Kura writes. The native Core/system-change locks remain the final process and packaging boundary. Other admitted/UNKNOWN system work blocks new adoption; only boot cancellation/reconciliation can settle a boot uncertainty while unrelated pending work still blocks them.

Only operation 15 is a retriable read. Prepared/execute/cancel/reconcile tasks use encrypted durable agent admissions and center payloads. A duplicate command or receipt query does not dispatch again. Changed or unreadable durable decisions on an error become UNKNOWN; partial kernel changes remain RECOVERY_REQUIRED and block new managed writes. Prepared or terminal policy scope remains separate from the task transport result. Policy receipts still have `bootVerified=false` and `kuraRecoveryVerified=false`.

Current receipt queries also support [original-command boot decision proof](ordinary-boot-task-outcome-v1.md). A native decision must atomically bind the exact admitted command to private immutable evidence; current enablement alone is insufficient. Legacy or incomplete evidence remains UNKNOWN. Explicit policy reconciliation does not itself update the original center task; the existing authenticated receipt query independently proves the original command after a complete native decision. This replaces the earlier pending resolver statement only within that contract's verified scope.

The bilingual console panel appears only for admin and this capability. It reads policy first, shows target/retirements/actions/digest/deadline, and requires explicit confirmation. A cancelled follow-up remains distinct from the retained confirmed policy. Refresh can read the original prepare task ID from session storage and rehydrate its authorization through the authenticated API; no token is stored in browser storage. Task creation uses a stable in-memory idempotency key for an unresolved request; UNKNOWN has no automatic resend or replacement-plan path. Boot prepare tokens are omitted from non-admin task views.

Full ordinary-profile handoff tasks, restart/reboot tasks, explicit native policy handover, non-native startup retirement, full Kura boot/business acceptance, complete release installation and the original remaining management scope are separate pending deliveries.

Validation of the final `centerboot2` candidate includes 170 host tests, 170 parallel Linux tests, strict Clippy, protocol/center/PostgreSQL and real HTTPS admission contracts, four mock browser scenarios and one actual mTLS center-to-agent browser flow. A fresh isolated full Kura was started through IDEA and its original GWT console was read. OrbStack used a separate actual full Kura ordinary process; center execution and an agent restart preserved its PID/InvocationID, selected DS/password/snapshot checks and GWT Count=9. This does not certify every Kura business component or a VM reboot.

The first candidate's real Parallels test exposed a missing initial UDS-frame allowlist entry before any boot action occurred. The final candidate permits all five administrative methods as a first frame, still denies them to a registered Kura peer with the same UID, and applies the existing long-write timeout/unknown-outcome treatment to its four mutations. A fresh Parallels fixture then passed public UDS, default-off/unbound operation, fixed-field rejection, real read-only mount EROFS, native enablement, cancellation and agent-restart persistence under the actual strict sandbox. Its target was explicitly a sleep stand-in; Java/Kura are absent there. The old failure and all state remain retained. No prior one-time entry was replayed.
